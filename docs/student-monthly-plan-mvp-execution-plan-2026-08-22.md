# Maestro Student App — Monthly Plan MVP Execution Plan

Дата подготовки: 22 августа 2026 года

Статус: план реализации, код этапа не изменён

Проект: `maestro-learning-platform`

## 1. Результат этапа

После реализации преподаватель сможет подготовить индивидуальный план ученика
на календарный месяц, сохранить его как черновик и отдельно опубликовать
ученику. Ученик увидит только опубликованную версию: цель месяца, упорядоченные
пункты, состояние каждого пункта и простой фактический прогресс.

MVP отвечает на пять вопросов:

1. Какова главная учебная цель ученика на этот месяц?
2. Какие конкретные пункты входят в план?
3. Что ещё запланировано, что сейчас в работе и что уже выполнено?
4. Опубликован ли план ученику?
5. Сколько пунктов выполнено из общего количества?

## 2. Входит ли дизайн

В этап входит функциональный дизайн самого Monthly Plan:

- понятный редактор в карточке ученика у преподавателя;
- состояния «Черновик», «Опубликовано» и «Есть неопубликованные изменения»;
- кнопка публикации ученику;
- компактный блок на главной ученика;
- отдельный экран с целью, пунктами и progress bar;
- состояния загрузки, ошибки и отсутствия плана;
- адаптация для телефона и PWA.

В этап не входит визуальный редизайн всей главной, новая нижняя навигация,
перестройка курсов, новые ранги, streak, XP или другие игровые механики.

## 3. Жёсткие границы MVP

### Входит

- только индивидуальный месячный план ученика;
- одна главная цель на один план;
- упорядоченный список пунктов;
- ровно три статуса пунктов;
- черновик преподавателя;
- явная публикация ученику;
- повторная публикация после исправлений;
- текущий календарный месяц по `Asia/Aqtobe`;
- несколько опубликованных планов, если у ученика несколько преподавателей;
- простой прогресс по выполненным пунктам;
- защита доступа и отсутствие внутренних заметок в student API;
- unit, integration, E2E и production smoke.

### Не входит

- групповой план в ученическом интерфейсе;
- объединение индивидуального и группового плана;
- автоматическое создание плана с помощью AI;
- согласование плана администратором;
- редактирование плана учеником или родителем;
- комментарии и чат внутри пунктов;
- дедлайны отдельных пунктов;
- вложения и материалы;
- начисление баллов или Coins за пункты;
- автоматическая связь пункта с уроком, ДЗ или тестом;
- история версий одного плана;
- push-уведомление о публикации;
- недельный или годовой план;
- аналитика качества работы преподавателя по планам.

Существующий `GroupMonthlyPlan` не удаляется и не переписывается в рамках MVP.

## 4. Подтверждённое исходное состояние

В проекте уже существует рабочая основа:

- Prisma-модель `StudentMonthlyPlan`;

- student read API;
- ученический тип Monthly Plan;

- единые правила прогресса;
- тесты месячного плана.

Также текущая локальная ветка требует безопасной синхронизации с обновившимся
`origin/main`. Реализацию нельзя начинать с автоматического pull/rebase поверх
грязного рабочего дерева.

## 5. Продуктовая модель

### 5.1 Владелец плана

План создаёт конкретный преподаватель для конкретного `crmStudentId` и месяца.
Текущий уникальный ключ сохраняется:

```text
crmStudentId + teacherUserId + month
```

Это означает, что ученик с двумя преподавателями может иметь два разных плана.
Student API обязан вернуть все опубликованные планы текущего месяца, а не
случайно выбрать один из них.

### 5.2 Содержимое опубликованного плана

Ученик видит только:

- месяц;
- имя преподавателя;
- главную цель;
- пункты в заданном преподавателем порядке;
- статус каждого пункта;
- количество выполненных пунктов;
- общее количество пунктов;
- процент выполнения;
- дату последней публикации.

Ученик не видит:

- `teacherUserId` как бизнес-данные интерфейса;
- внутреннюю заметку преподавателя;
- черновые правки;
- финансовые данные;
- информацию о зарплате;
- ожидаемый результат, skills и checkpoint до отдельного продуктового решения.

Существующие поля `expectedResult`, `skills`, `checkpoint` и `note` не удаляются
из базы и не ломаются. Они остаются teacher-only legacy-полями, но не входят в
student DTO этого MVP.

### 5.3 Три статуса пунктов

Разрешены ровно три значения:

| Код | Текст | Значение |
|---|---|---|
| `planned` | Запланировано | Пункт входит в план, работа ещё не начата |
| `in_progress` | В работе | Ученик и преподаватель сейчас работают над пунктом |
| `completed` | Выполнено | Преподаватель считает пункт выполненным |

Статус `moved` больше не используется в индивидуальном плане. Перенос — это
действие преподавателя, а не состояние результата. Существующие пункты со
статусом `moved` необходимо безопасно нормализовать в `planned`, сохранив `id`,
текст и порядок.

Преподаватель может вручную перевести пункт в любой из трёх статусов. В MVP не
нужна строгая state machine, потому что преподаватель должен иметь возможность
исправить ошибочно выбранный статус.

### 5.4 Правило прогресса

Прогресс считается только по опубликованному snapshot:

```text
completed = количество пунктов со статусом completed
total = количество опубликованных пунктов
percent = round(completed / total * 100)
```

Правила:

- `planned` даёт 0%;
- `in_progress` даёт 0%, частичного зачёта нет;
- `completed` считается полностью;
- если выполнены все пункты, прогресс равен 100%;
- пустой план публиковать нельзя;
- порядок пунктов не влияет на процент;
- прогресс не начисляет Points или Coins;
- прогресс не является уровнем ученика и не смешивается с прогрессом курса.

Пример: два выполненных пункта из пяти дают `40%`.

### 5.5 Черновик и публикация

Сохранение и публикация — разные действия.

1. Преподаватель редактирует и сохраняет черновик.
2. Пока план не опубликован, ученик его не видит.
3. При публикации backend создаёт неизменяемый для student API snapshot текущего
   черновика.
4. После публикации преподаватель может продолжить редактирование черновика.
5. Эти изменения не видны ученику до повторной публикации.
6. После повторной публикации student snapshot полностью заменяется актуальной
   версией.

Такой контракт предотвращает ситуацию, когда ученик видит наполовину
заполненный план во время работы преподавателя.

## 6. Модель данных

### 6.1 Изменения Prisma

В `StudentMonthlyPlan` добавить:

```prisma
publishedSnapshot Json?     @map("published_snapshot") @db.JsonB
publishedAt       DateTime? @map("published_at") @db.Timestamptz(6)
draftRevision     Int       @default(1) @map("draft_revision")
publishedRevision Int       @default(0) @map("published_revision")
```

Назначение полей:

- `items`, `goal` и остальные текущие поля — редактируемый черновик;
- `publishedSnapshot` — единственный источник student read API;
- `publishedAt` — время последней успешной публикации;
- `draftRevision` увеличивается при каждом сохранении черновика;
- `publishedRevision` получает значение `draftRevision` при публикации;
- `draftRevision > publishedRevision` означает наличие неопубликованных
  изменений.

В snapshot хранить только версионированный публичный контракт:

```json
{
  "schemaVersion": 1,
  "goal": "Уверенно менять основные аккорды без остановки",
  "items": [
    {
      "id": "uuid",
      "title": "Переход Em — Am",
      "status": "in_progress"
    }
  ]
}
```

Не записывать в snapshot внутреннюю заметку, телефон, баланс, CRM payload или
другие персональные данные.

### 6.2 Миграция

Создать новую отдельную миграцию. Не редактировать уже существующую миграцию
`20260724160000_student_monthly_plans`.

Миграция должна:

1. добавить четыре новых поля с безопасными defaults;
2. оставить существующие планы черновиками, то есть не публиковать их
   автоматически;
3. заменить `moved` на `planned` внутри `items` без удаления элементов;
4. не создавать snapshot для старых планов;
5. не изменять `GroupMonthlyPlan`;
6. быть обратимо безопасной на уровне приложения: старые строки остаются
   читаемыми после deploy новой версии.

Помимо SQL-нормализации backend должен иметь defensive normalization:
неизвестный старый статус в teacher draft отображается как `planned`, но student
API никогда не возвращает неизвестный статус.

## 7. Backend-контракты

### 7.1 Общий доменный модуль

Создать отдельный чистый модуль, например:

```text
backend/src/domain/monthly-plan.ts
```

В него вынести:

- тип трёх статусов;
- нормализацию старого `moved`;
- sanitization пунктов;
- проверку уникальности `id`;
- расчёт `completed`, `total`, `percent`;
- построение публичного snapshot;
- проверку snapshot `schemaVersion`.

Расчёт прогресса не должен дублироваться в двух сервисах и во frontend.

### 7.2 Teacher GET

Сохранить существующий endpoint:

```http
GET /api/v1/teachers/me/students/:crmStudentId/monthly-plan?month=YYYY-MM
```

Расширить ответ:

```json
{
  "data": {
    "student": {
      "crmStudentId": "...",
      "name": "Имя ученика"
    },
    "month": "2026-08",
    "plan": {
      "id": "uuid",
      "goal": "Цель",
      "items": [],
      "progress": {
        "completed": 0,
        "total": 0,
        "percent": 0
      },
      "publication": {
        "isPublished": false,
        "publishedAt": null,
        "draftRevision": 2,
        "publishedRevision": 0,
        "hasUnpublishedChanges": true
      },
      "updatedAt": "ISO"
    }
  }
}
```

Teacher response может продолжить возвращать legacy-поля для сохранения
существующего функционала, но student response их не использует.

### 7.3 Teacher PUT — сохранить черновик

Сохранить endpoint:

```http
PUT /api/v1/teachers/me/students/:crmStudentId/monthly-plan
```

Правила:

- только teacher с `offline_school.write`;
- ученик должен быть назначен преподавателю;
- `month` имеет формат `YYYY-MM`;
- `goal` максимум 500 символов;
- до 20 пунктов в индивидуальном MVP;
- заголовок пункта максимум 300 символов;
- `id` обязателен и уникален в рамках плана;
- статус только один из трёх;
- пустые пункты удаляются до записи;
- сохранение увеличивает `draftRevision` ровно один раз только при фактическом
  изменении нормализованных данных;
- повторный запрос с полностью совпадающими данными идемпотентен и не меняет
  revision;
- сохранение не меняет `publishedSnapshot`, `publishedAt` и
  `publishedRevision`;
- API возвращает нормализованный draft, progress и publication state.

Черновик разрешено сохранить без цели и пунктов. Ограничения «цель обязательна»
и «минимум один пункт» применяются только при публикации.

### 7.4 Teacher POST — публикация

Добавить endpoint:

```http
POST /api/v1/teachers/me/students/:crmStudentId/monthly-plan/publish
```

Body:

```json
{
  "month": "2026-08",
  "expectedDraftRevision": 3
}
```

Правила публикации:

1. Повторно проверить назначение ученика преподавателю.
2. Найти plan по текущему уникальному ключу.
3. Если план не найден, вернуть `404 MONTHLY_PLAN_NOT_FOUND`.
4. Если revision не совпал, вернуть `409 MONTHLY_PLAN_STALE_DRAFT`.
5. Trim цели и пунктов ещё раз на backend.
6. Если цель пуста, вернуть `400 MONTHLY_PLAN_GOAL_REQUIRED`.
7. Если пунктов нет, вернуть `400 MONTHLY_PLAN_ITEMS_REQUIRED`.
8. Если есть неизвестный статус или повторяющийся id, вернуть `400` с понятным
   кодом.
9. Если этот `draftRevision` уже опубликован, вернуть существующий snapshot с
   `idempotent: true`, не менять дату и не создавать повторное audit-событие.
10. В одной транзакции создать snapshot, записать `publishedAt` и приравнять
   `publishedRevision` к `draftRevision`.
11. Вернуть опубликованную версию, publication state и `idempotent`.

Публикация не начисляет награды и не отправляет сообщение родителю.

### 7.5 Student GET

Добавить endpoint:

```http
GET /api/v1/students/me/monthly-plans?month=YYYY-MM
```

Параметр `month` необязательный. Без него backend использует текущий месяц в
`Asia/Aqtobe`.

Защита:

- `authenticate`;
- `requireStudent`;
- `requirePermission("progress.read")`;
- `crmStudentId` берётся только из авторизованного `User`;
- клиент не может передать чужой `crmStudentId`;
- если профиль не связан с CRM, вернуть `400 CRM_NOT_LINKED`;
- читать только строки с ненулевым `publishedSnapshot` и `publishedAt`;
- draft-поля не включать в select/DTO ответа.

Ответ:

```json
{
  "data": {
    "month": "2026-08",
    "plans": [
      {
        "id": "uuid",
        "teacher": {
          "name": "Иван Петров"
        },
        "goal": "Уверенно менять основные аккорды",
        "items": [
          {
            "id": "uuid",
            "title": "Переход Em — Am",
            "status": "in_progress"
          }
        ],
        "progress": {
          "completed": 2,
          "total": 5,
          "percent": 40
        },
        "publishedAt": "ISO"
      }
    ],
    "aggregateProgress": {
      "completed": 2,
      "total": 5,
      "percent": 40
    }
  }
}
```

Если опубликовано несколько планов, `plans` содержит каждый план отдельно, а
aggregate progress считается по всем опубликованным пунктам. Сортировка
детерминированная: имя преподавателя, затем `id`.

Если планов нет, вернуть `200` и пустой массив, а не `404`.

### 7.6 Аудит

Записать audit events:

- `monthly_plan_draft_saved`;
- `monthly_plan_published`;
- `monthly_plan_republished`.

В audit payload разрешены month, количество пунктов, revisions и процент. Не
записывать полный текст цели и пунктов, чтобы не раздувать лог и не дублировать
учебные данные.

## 8. Frontend преподавателя

### 8.1 Размещение

Использовать существующий `StudentMonthlyPlanEditor` в карточке ученика. Не
создавать второй независимый редактор.

### 8.2 Поля MVP

Главный рабочий блок содержит:

1. выбор месяца;
2. поле «Главная цель месяца»;
3. список пунктов;
4. статус каждого пункта;
5. удаление и добавление пункта;
6. preview прогресса;
7. publication state;
8. кнопки «Сохранить черновик» и «Опубликовать ученику».

Legacy-поля нельзя удалять из данных. Если они остаются на экране, визуально
отделить их как teacher-only дополнительные заметки. Они не должны создавать
ощущение, что ученик увидит эти поля.

### 8.3 Publication UX

Показывать одно из состояний:

- `Черновик` — публикации ещё не было;
- `Опубликовано ученику · дата/время` — draft и snapshot совпадают;
- `Есть неопубликованные изменения` — draftRevision больше publishedRevision.

Поведение кнопок:

- изменение поля сразу снимает локальный флаг «сохранено»;
- «Сохранить черновик» сохраняет, но не публикует;
- «Опубликовать ученику» сначала сохраняет текущую форму, затем публикует
  полученный `draftRevision`;
- во время обоих запросов кнопки блокируются;
- двойной клик не создаёт две публикации;
- после `409 MONTHLY_PLAN_STALE_DRAFT` редактор предлагает обновить данные;
- после ошибки публикации сохранённый draft не теряется;
- перед первой публикацией показать короткое подтверждение: «Ученик увидит цель
  и все пункты плана»;
- повторная публикация называется «Обновить план ученику».

### 8.4 Preview прогресса

В редакторе показывать:

```text
Выполнено 2 из 5 · 40%
```

Это preview текущего draft. Рядом с опубликованным состоянием не смешивать его
со student snapshot, если есть неопубликованные изменения.

## 9. Frontend ученика

### 9.1 API и типы

Добавить отдельные student-типы. Не использовать teacher DTO в ученическом
интерфейсе.

Добавить в API client:

```text
api.studentMonthlyPlans(month?)
```

### 9.2 Компактный блок на главной

Monthly Plan загружается как второстепенный ресурс через существующий
`Promise.allSettled`. Ошибка Monthly Plan не должна скрывать всю главную.

Если опубликован один план, блок показывает:

- «План на август»;
- цель;
- progress bar;
- «2 из 5 выполнено»;
- кнопку «Открыть план».

Если планов несколько, блок показывает:

- количество планов;
- aggregate progress;
- первый незавершённый пункт либо нейтральный текст;
- кнопку «Открыть планы».

Если текущего опубликованного плана нет, не показывать большую пустую карточку
на главной. Это не должно визуально наказывать ученика за то, что преподаватель
ещё не опубликовал план.

### 9.3 Отдельный экран

Добавить маршрут:

```text
/monthly-plan
```

Экран показывает для каждого опубликованного плана:

- месяц;
- имя преподавателя;
- цель;
- progress bar и точные числа;
- все пункты в исходном порядке;
- текстовый статус и иконку каждого пункта;
- дату обновления плана.

Статусы нельзя обозначать только цветом:

- круг/точка + «Запланировано»;
- активный индикатор + «В работе»;
- check icon + «Выполнено».

Ученик не может менять статусы.

### 9.4 Состояния экрана

- loading: skeleton или короткий loader без старого интерфейса;
- empty: «Преподаватель ещё не опубликовал план на этот месяц»;
- `CRM_NOT_LINKED`: «Профиль школы не подключён. Обратитесь к администратору»;
- network/server error: локальная ошибка и кнопка «Повторить»;
- invalid snapshot одной записи: пропустить повреждённую запись, залогировать
  ошибку и не ронять остальные планы.

## 11. Обязательные тесты

### Unit

- `planned`, `in_progress`, `completed` принимаются;
- `moved` нормализуется в `planned` только для legacy draft;
- неизвестный статус не попадает в snapshot;
- пустой список даёт `0/0/0`, но publish validation его отклоняет;
- `0/5 = 0%`;
- `2/5 = 40%`;
- `5/5 = 100%`;
- duplicate item id отклоняется;
- trim не меняет id и порядок;
- snapshot не содержит `note` и legacy-поля.

### Integration

- назначенный преподаватель сохраняет draft;
- неназначенный преподаватель получает отказ;
- draft невидим ученику;
- publish без goal отклонён;
- publish без пунктов отклонён;
- stale revision получает `409`;
- первая публикация создаёт snapshot;
- изменение draft не меняет опубликованный response;
- republish меняет student response;
- unlinked student получает `CRM_NOT_LINKED`;
- linked student видит только свои планы;
- два преподавателя дают два плана;
- teacher note не утекла в student JSON.

### Frontend/E2E

- teacher создаёт цель и три пункта;
- выбирает каждый из трёх статусов;
- видит draft progress;
- сохраняет и публикует;
- student dashboard показывает карточку;
- student page показывает цель, пункты и 33% для одного выполненного из трёх;
- teacher меняет второй пункт на completed без публикации — student всё ещё видит
  старую версию;
- teacher повторно публикует — student видит 67%;
- ошибка Monthly Plan API не роняет dashboard;
- мобильная ширина не создаёт горизонтальный scroll;
- после PWA update отображается новая версия.

## 12. P0 сценарии приёмки

### P0-1. План не опубликован

1. Преподаватель создаёт draft на текущий месяц.
2. Указывает цель и три пункта.
3. Сохраняет.
4. Ученик открывает приложение.

Ожидаемо: draft у преподавателя сохранён, ученик его не видит.

### P0-2. Первая публикация

1. Преподаватель нажимает «Опубликовать ученику».
2. Backend создаёт snapshot.
3. Ученик обновляет главную.

Ожидаемо: ученик видит цель, три пункта и `0 из 3 · 0%`.

### P0-3. Простой прогресс

1. Преподаватель отмечает один пункт выполненным.
2. Повторно публикует.

Ожидаемо: ученик видит `1 из 3 · 33%`; `in_progress` не считается частично.

### P0-4. Неопубликованное исправление

1. Преподаватель меняет второй пункт.
2. Только сохраняет draft.

Ожидаемо: teacher UI сообщает о неопубликованных изменениях, student view не
изменился.

### P0-5. Несколько преподавателей

1. Два назначенных преподавателя публикуют разные планы.
2. Ученик открывает `/monthly-plan`.

Ожидаемо: видны оба плана с отдельными целями и прогрессом; ничего не выбирается
случайно.

### P0-6. Защита данных

1. Ученик пытается подставить чужой CRM id.
2. Проверяется student API response.

Ожидаемо: endpoint не принимает CRM id; внутренние teacher notes отсутствуют.

## 14. Порядок коммитов

Не смешивать MVP с Foundation и group plan работой. Рекомендуемые коммиты:

1. `feat(monthly-plan): add publication snapshot contract`
2. `feat(monthly-plan): expose published plans to students`
3. `feat(monthly-plan): add teacher publish workflow`
4. `feat(monthly-plan): show published plan to students`
5. `test(monthly-plan): cover publication and progress flows`

Перед каждым commit проверить staged diff и не включать посторонние dirty-файлы.

## 15. Production rollout

1. Зафиксировать предыдущий production SHA.
2. Создать backup БД.
3. Применить миграцию.
4. Развернуть backend и web одним release SHA.
5. Проверить `/health` и web meta.
6. Выполнить read-only smoke.
7. Авторизоваться тестовым преподавателем и учеником.
8. Проверить P0-1 — P0-4 на отдельном тестовом плане, не меняя планы реальных
   учеников.
9. В течение 30 минут проверить backend logs, frontend exceptions и 4xx/5xx
   нового API.

Откат приложения выполняется на предыдущий SHA. Если миграция уже применена,
новые nullable/default-поля можно оставить: они не ломают предыдущую версию.

## 16. Definition of Done

Monthly Plan MVP завершён только если:

- у индивидуального плана ровно три публичных статуса;
- преподаватель может сохранить draft;
- draft не виден ученику;
- преподаватель может явно опубликовать и повторно опубликовать план;
- ученик видит только snapshot текущего месяца;
- цель, пункты и статусы отображаются корректно;
- progress считается как completed/total;
- несколько преподавателей не конфликтуют;
- внутренние поля не попадают в student API;
- ошибка plan API не роняет главную;
- desktop и PWA проверены;
- backend/frontend regression и E2E зелёные;
- production SHA подтверждён;
- существующие Foundation, teacher/offline и group plan изменения сохранены.
