# Техническая карта изменений Maestro

Статус: `MAIN RECONCILED / DEV-04S AND DEV-07A..DEV-07E DONE LOCALLY / RELEASE GATES REMAIN`
Назначение: переход от текущего приложения к утверждённой продуктовой модели
Основание: документы [01](./01-product-constitution.md), [02](./02-role-screen-map.md), [03](./03-process-event-map.md)

## 1. Шкала сложности

Оценка включает backend, frontend, миграцию, тесты и связи:

| Код | Оценка | Смысл |
|---|---|---|
| `S` | малая | локальная правка без новой модели данных |
| `M` | средняя | несколько модулей или небольшая миграция |
| `L` | большая | новый сквозной процесс и несколько ролей |
| `XL` | очень большая | отдельная подсистема, real-time или высокорисковая миграция |

Оценка времени не фиксируется до утверждения объёма этапа.

### 4.1 Что не проектируется в V1

Следующие функции не получают таблицы, API, пункты меню, пустые состояния,
feature flags или визуальные заготовки: общий школьный чат, личные сообщения
между учениками, сезон, публичный годовой приз, автоматический складской резерв
награды, портфолио, репертуар, концерты как продуктовый модуль и произвольная
аналитическая платформа. Существующие универсальные журналы могут хранить
события без создания отдельного продуктового контура.

## 6. Целевая модель данных

Точные поля и enum проектируются по подтверждённым правилам документа 03 внутри соответствующего DEV-пакета. Минимально потребуются:

- учебная тема ученика;
- связь темы с направлением и месячными планами;
- версионируемый состав месячного плана с автором и временем изменения;
- состояние связи темы с версией плана: действующая, перенесённая или заменённая;
- неизменяемая история процента;
- ДЗ занятия;
- обязательная связь ДЗ ровно с одной нормализованной учебной темой и необязательная ссылка на урок-источник;
- необязательный сохранённый `dueAt`; дата следующего урока из CRM используется только как предлагаемое начальное значение и не остаётся живой связью после сохранения;
- попытка ДЗ с собственным статусом проверки, включая «ожидает проверки», и способом отправки `materials` или `ready_for_lesson`;
- неизменяемые версии ответа внутри одного цикла сдачи и отдельный номер цикла доработки;
- проверка попытки;
- материалы и защищённые вложения;
- унифицированная проекция урока с CRM ID, `classType`, `deliveryFormat`, `roomId/roomName`, `meetingUrl`, преподавателем, участниками, расписанием и версией источника;
- учебный диалог и участники;
- сообщения, прочтения, жалобы и аудит;
- разрешения родительского доступа;
- единый журнал доменных событий или outbox.
- финальный снимок результата каждого участника недельной лиги.
- конфигурация границ `LEVEL 1–10` и неизменяемая история достижения LEVEL;
- состояние текущей и лучшей серии, результат каждой недели и причина защиты;

Тема не хранит статус «ожидает проверки». Этот сигнал вычисляется для интерфейса по наличию активной отправленной попытки, поэтому несколько ДЗ одной темы не перезаписывают состояние друг друга.

Решение по ДЗ и изменение процента темы выполняются двумя явными командами. API принятия ДЗ не имеет права неявно ставить теме 100%, а команда процента темы не должна подменять статус попытки.

Первая попытка для XP и статистики определяется отсутствием предыдущего возврата преподавателем, а не количеством версий, отправленных до проверки. Версии одного цикла не увеличивают `acceptedCount`, число циклов или награду.

### 6.1 Очередь проверки преподавателя

`CURRENT TECH-GAP-001`: текущий интерфейс показывает общую очередь «Проверка ДЗ» только контентным администраторам. У преподавателя нет пункта или счётчика очереди, list/detail API требуют контентную административную роль, а уведомление о новой работе может вести преподавателя по недоступной ссылке.

Целевой контракт:

- совместимый URL очереди сохраняется, но интерфейс и API становятся ролевыми;
- преподаватель получает серверный список и счётчик только по назначенным ему ученикам/группам из CRM;
- существующая административная роль получает общую очередь школы;
- ограничения применяются отдельно к списку, карточке, истории попыток и команде проверки; frontend-фильтр не считается защитой;
- прямой запрос преподавателя к чужой попытке не раскрывает ученика, текст, файлы или историю;
- счётчик, экран «Сегодня», очередь, карточка ученика и урок используют один серверный запрос/проекцию и одинаковое определение статуса;
- уведомление создаётся только ответственному преподавателю и куратору, содержит ID попытки и ведёт в доступную карточку;
- повторная доставка события не создаёт вторую попытку, второй счётчик или второе уведомление;
- обновлённая версия до решения преподавателя остаётся в той же строке очереди, а предыдущая версия доступна в истории;
- переназначение открытых попыток следует подтверждённым раздельным правилам постоянной смены и разовой замены преподавателя.

Назначения CRM различаются по типу:

- постоянная смена ответственного преподавателя обновляет server-side scope открытых ДЗ, сохраняет прежних авторов в аудите и не создаёт копии попыток;
- разовая замена содержит ID конкретного урока и временного преподавателя, даёт доступ только к уроку/отчёту и не изменяет owner/scope ДЗ, планов, тем и диалогов;
- если после постоянной смены новый преподаватель не назначен, открытые работы остаются доступными куратору;
- повтор события постоянной или разовой замены применяется идемпотентно.

Отчёт урока хранит неизменяемые отправленные версии и отдельный текущий статус. До CRM-подтверждения только автор отчёта может выполнить явный отзыв и создать редактируемую версию. После подтверждения новый цикл исправления создаёт куратор с обязательной причиной; прямой `update` подтверждённой версии запрещён на сервере. Разовый заменяющий преподаватель получает эти права только для ID назначенного урока. Если исходный отчёт уже связан со списанием или зарплатой, приложение не переписывает финансовую запись и передаёт в CRM команду отдельной идемпотентной корректировки со ссылками на исходный отчёт, его версию и причину.

Аудит отчёта обязан сохранять автора версии, автора отзыва/переоткрытия, причину, время, статус подтверждения и связанные идентификаторы CRM. Проверки прав применяются к чтению истории, отзыву, повторной отправке и переоткрытию отдельно.

`CONFIRMED TECH-LESSON-DRAFT-001`: текущий браузерный draft сохраняется как мгновенная страховочная копия, а целевая серверная модель хранит `lessonId`, `ownerId`, payload формы, монотонную `revision`, `updatedAt` и срок удаления. Сохранение принимает ожидаемую ревизию и возвращает конфликт вместо last-write-wins. Читать и изменять содержимое может только автор; кураторский endpoint возвращает только наличие и время обновления. Разовая замена проверяется по конкретному CRM lesson ID. Успешная отправка отчёта атомарно создаёт неизменяемую версию и очищает активный draft. Фоновая очистка удаляет неотправленные черновики через 30 дней после урока.

`CONFIRMED TECH-TEACHER-HISTORY-001`: доступ к истории вычисляется на сервере по активному постоянному назначению `teacher + student/group + direction` из CRM. Read-модель включает планы, темы, историю прогресса, официальные итоги уроков, ДЗ, версии попыток, разрешённые файлы, проверки, авторов и даты. Она исключает административные заметки, финансы/зарплату, поля `salesSignals`, служебные комментарии пробного и сообщения диалога с прежним преподавателем. List, detail, download и history endpoints применяют одинаковый scope; URL файла не обходит проверку. Разовая замена lesson ID не расширяет scope истории. Завершение назначения отзывает чтение, не удаляя аудит авторства.

`CONFIRMED TECH-STUDENT-HOME-001`: backend/read-model возвращает тип и ID одного `primaryAction` по утверждённому приоритету, а не перекладывает сортировку на отдельные frontend-компоненты. Дедупликация не позволяет одному ДЗ одновременно появиться главным действием и отдельной срочной карточкой. `waiting_review` исключается из action-кандидатов. При равном типе используется ближайший срок, затем `createdAt`, затем стабильный ID. Desktop и mobile используют одну семантику; mobile-верстка имеет одну колонку и проверяется на 320, 375 и 430 px без горизонтальной прокрутки.

Сложность: `M` внутри `DEV-03`. Основные связи: CRM-назначение преподавателя, RBAC, персональные данные ученика, вложения, push/in-app уведомления и шаг проверки внутри урока.

`CONFIRMED TECH-DATA-001`: тема ученика или группы не перемещается и не копируется физически между месяцами. Отдельная версионируемая связь включает одну тему в разные планы, а reward source остаётся идентификатором темы, поэтому перенос не создаёт вторую историю или награду.

`CONFIRMED TECH-GROUP-001`: групповая тема хранится одной сущностью с `groupId`, единым процентом и единой историей изменений. Участники группы не получают копии темы или отдельные проценты. Общее `HomeworkAssignment` связано с групповой темой, а отдельный `HomeworkRecipient` создаётся идемпотентно для каждого активного участника, включая отсутствовавшего на уроке. Посещение, попытки, проверки, комментарии и статистика адресуются конкретному ученику.

`CONFIRMED TECH-TRIAL-001`: существующий `TrialLessonReport` остаётся отдельной моделью/проекцией и не создаёт `LearningTopic`, `MonthlyPlan`, `HomeworkAssignment` или наградную транзакцию. Значение `lessonFacts.homeworkGiven` является только полем диагностического отчёта. Активация ученика из CRM сохраняет связь с пробным отчётом для чтения, но создание первого плана, тем и ДЗ выполняется отдельными командами с собственными source ID. Повторный пробный использует тот же диагностический контракт и не входит в лигу.

## 7. CRM-синхронизация

Обязательные свойства:

- входящие события имеют внешний ID и версию/время изменения;
- справочник направлений и его идентификаторы принадлежат CRM; приложение хранит только синхронизированную проекцию для связей, фильтров и отображения;
- CRM сообщает отдельно постоянное назначение преподавателя и разовую замену конкретного урока; приложение не выводит постоянную смену из факта проведения одного замещённого занятия;
- создание, переименование и архивирование направления в приложении запрещено;
- повтор одного события безопасен;
- удаление сотрудника или ученика архивирует связь, но не историю;
- приложение показывает время последней успешной синхронизации;
- временная недоступность CRM не уничтожает локальные учебные данные;
- конфликт фиксируется в журнале и не разрешается скрытой перезаписью.

`CONFIRMED TECH-CRM-001`: приложение отправляет посещаемость и отчёт через идемпотентную очередь с последующим подтверждением CRM. Для уже синхронизированного урока временный сбой не блокирует учебный сценарий: локальная серверная запись получает статус `pending_sync`, число попыток и последняя ошибка видны куратору, а повторная доставка не дублирует события. Списание, зарплата и XP за посещение создаются только после подтверждения CRM. Создание преподавателем официального урока без CRM ID и записи в локальной проекции запрещено.

`CONFIRMED TECH-CRM-002`: синхронизация использует field ownership matrix. CRM-owned: расписание, тип и формат урока, кабинет, ссылка подключения, состав группы, направление, постоянные/разовые назначения и подтверждённая посещаемость. App-owned: планы, темы, ДЗ, попытки, проверки, файлы и учебные комментарии. Внешние события содержат `externalId` и монотонную версию; старая версия идемпотентно игнорируется и журналируется.

`CONFIRMED TECH-CRM-003`: CRM-модель урока хранит `deliveryFormat = offline | online` с безопасным default `offline` и необязательный `meetingUrl`. Для онлайн-урока `roomId` отсутствует; для очного урока `meetingUrl` очищается. Integration read endpoints возвращают эти поля во всех lesson summary/detail проекциях. Learning Platform использует один list/detail/report flow и фильтрует проекцию по формату. Создание новых записей старой online-request модели по умолчанию отвечает `409 ONLINE_LESSONS_MANAGED_IN_CRM`; чтение старой истории сохраняется на период совместимости, а аварийное включение записи возможно только явным локальным feature flag.

Отличие подтверждённой посещаемости CRM от отправленной отметки преподавателя создаёт запись конфликта с обеими версиями, но финансовая и XP-проекция читает CRM-значение. Изменение состава/расписания помечает активный draft как требующий сверки и не удаляет payload. Перед отправкой автор подтверждает актуальный roster version. Конфликт без утверждённого владельца разрешает куратор с обязательной причиной; разрешение создаёт новую версию и не переписывает аудит исходных данных.

## 8. Награды и транзакции

- каждый источник имеет уникальный idempotency key;
- бизнес-событие и транзакция начисления связываются явным source ID;
- исправление выполняется новой обратной транзакцией;
- повторный запрос возвращает существующий результат;
- `CONFIRMED TECH-LEAGUE-HISTORY-001`: финализация недели создаёт неизменяемый snapshot на ученика с границами недели и timezone, place в общей таблице, XP total, goal state, awarded Coins, streak state, personal position и top-3 projection. Отдельные source-строки XP сохраняются для расшифровки. History endpoint возвращает восемь недель на первую страницу и cursor pagination для полного архива; старые снимки не вычисляются из текущих балансов или текущего состава общей таблицы.
- `CONFIRMED TECH-LEAGUE-FINALIZE-001`: неделя использует `Asia/Aqtobe`, закрывает приём обычных пользовательских событий в воскресенье 23:59:59 и остаётся `finalizing` до понедельника 12:00. Отложенное CRM-событие включается по immutable `occurredAt`, если доставлено до финализации. Один идемпотентный job в 12:00 создаёт snapshot и Coin-транзакции. После `finalized` поздние события журналируются, но не запускают автоматический rerank/reward reversal. Компенсация и отмена создают отдельные source-транзакции с автором и причиной; исходный snapshot не обновляется in-place.
- `CONFIRMED TECH-POINTS-LEADERS-001`: отдельный read endpoint строит текущий top по `PointsLedger` только новой economic epoch, возвращает top-10 и позицию авторизованного ученика. Равные Points получают одинаковый rank; стабильная сортировка внутри равенства нужна только для порядка строк. Endpoint не читает недельный XP snapshot и не создаёт награды.
- уведомление создаётся только после успешной транзакции;
- ручное начисление требует права, причины, лимита и аудита;
- экономика проверяется симуляцией до миграции LEVEL.
- постоянный LEVEL рассчитывается только из Points;
- XP-события относятся к конкретной неделе, но сохраняются после её окончания;
- финальный результат недели хранится отдельно от текущего live-расчёта;
- самостоятельные курсы и тесты не создают постоянные Points вне закрытия темы.
- Points и LEVEL общие для всех направлений, но тема и план всегда имеют направление;
- закрытие темы и начисление 100 Points выполняются сразу одной защищённой операцией;
- закрытие последней темы непустого плана и бонус 250 Points также защищены единым source ID;
- проверка закрытия использует только действующие темы актуальной версии плана; добавленная тема обязательна, а перенесённая или заменённая исключается без удаления истории;
- после закрытия и начисления бонуса обычное редактирование состава плана запрещено;
- после подтверждения занятия в CRM первые два подходящих занятия ученика за неделю суммарно по всем направлениям начисляют по 20 XP и 50 Coins; последующие не начисляют XP/Coins;
- недельные лимиты ДЗ, тестов и бонусов проверяются сервером до создания XP-события.
- событие посещения после исчерпания недельного XP-лимита остаётся доступным расчёту серии и не создаёт нулевую XP-транзакцию;
- целевой `LEVEL 10` достигается примерно за двенадцать типовых месячных планов одного направления;
- достижение каждого LEVEL и каждой медали имеет отдельный идемпотентный source ID;
- серия недели определяется сервером только по подтверждённому посещению или принятому ДЗ, а не по frontend-активности;
- каникулы, отмена всех занятий и ручная защита серии сохраняют аудируемую причину;
- `CONFIRMED TECH-STREAK-PROTECTION-001`: автоматическая защита создаётся идемпотентно из CRM-события каникул, официальной паузы абонемента или отмены всех занятий недели. Ручная команда доступна только куратору, принимает категорию, комментарий и исходную неделю, проверяет срок семь календарных дней и сохраняет автора/время; attachment необязателен. Преподаватель создаёт только recommendation/request без изменения серии. Frozen week не входит в streak increment, medal counter или reward ledger. Поздняя административная корректировка создаёт отдельную версию и не переписывает исходный weekly snapshot.
- `CONFIRMED TECH-STREAK-MILESTONE-001`: при первом достижении 4/8/12/24/52 недель одна транзакция финализации создаёт постоянную медаль и Coin-награду 50/100/150/250/500. Уникальный source key содержит student ID и milestone, поэтому повторное достижение, повтор job или восстановление серии не дублируют медаль/Coins. Frozen week не увеличивает milestone counter. Отмена ошибочного рубежа выполняется отдельной аудируемой обратной транзакцией и не удаляет исходное событие.
- `CONFIRMED TECH-REWARD-SHOP-001`: наградная витрина хранит ссылку на product ID и variant/SKU, отдельную Coin-цену и статус публикации. Коммерческая цена в тенге не участвует в Coin-списании. Создание запроса атомарно проверяет баланс и списывает полную Coin-цену; mixed payment endpoint отсутствует. Куратор вручную переводит запрос в `fulfilled` или `declined` с причиной. При отказе создаётся компенсирующая Coin-транзакция. Ни один статус первого выпуска не вызывает складской резерв, коммерческий заказ или inventory movement.
- `CONFIRMED TECH-COMM-SCOPE-001`: типы первого выпуска ограничены `learning_direction`, `parent_teacher`, `curator` и `crm_group`. Учебный и общий родительский диалоги scoped к ученику, постоянному преподавателю и направлению; родительский membership содержит всех активных родителей, но не ребёнка. Разовая lesson replacement не добавляет membership. Групповой чат синхронизирует активных учеников и преподавателя из CRM, куратор имеет модерирующий scope. Student-to-student DM и school-wide room endpoints отсутствуют. Завершение назначения переводит прежние диалоги в read-only, новый преподаватель получает новые scope, а возврат того же преподавателя возобновляет прежние scope с сохранённой историей.
- `CONFIRMED TECH-COMM-MODERATION-001`: message хранит неизменяемые версии; edit/retract command проверяет автора и окно 15 минут. Видимая запись содержит `editedAt` либо tombstone, исходник доступен только curator audit endpoint. Report фиксирует конкретную version ID. Hide/restrict требуют куратора, причины и срока ограничения; состав CRM-группы администратор вручную не меняет. MIME allowlist чата ограничена безопасными изображениями, видео MP4/MOV/WebM, PDF и аудио, до пяти файлов по 50 MB. Conversation text/version/audit удаляются через три года после закрытия, blob вложений — через двенадцать месяцев, после чего сохраняются hash, MIME, размер, автор и временные метаданные без содержимого файла.
- `CONFIRMED TECH-GUARDIAN-001`: `GuardianAccess` связывает отдельного взрослого, ребёнка, CRM/ручное основание, автора, время выдачи и отзыва. Все guardian endpoints используют allowlist read-полей; attempts, file download, private learning conversation, internal notes, other students, Coin mutations и reward requests запрещены сервером. Несколько активных связей равноправны. Ученик получает безопасную проекцию имён взрослых с доступом.
- `CONFIRMED TECH-CONSENT-001`: договорное согласие синхронизируется отдельной CRM-проекцией с contract ID/version, guardian ID, scopes, validFrom/validTo и revokedAt. Создание публикации или иного consent-required действия проверяет актуальную проекцию сервером; frontend-флаг не является защитой. Отзыв блокирует новые действия, не удаляет автоматически ранее созданные учебные записи и не подменяет отдельный статус `GuardianAccess`.
- `CONFIRMED TECH-ADMIN-JOURNAL-001`: единая таблица/проекция журнала хранит type, severity, source, linked entity, status `new/in_progress/resolved/dismissed`, createdAt, updatedAt, resolution и неизменяемую историю действий. Поле assignee отсутствует в V1. Записи создаются идемпотентно из жалоб, модерации, CRM/sync ошибок, зависших проверок и отчётов, корректировок наград и изменений родительского доступа. List endpoint сортирует severity затем возраст, поддерживает фильтры и общий scope единой административной роли. Автоматический SLA-таймер и эскалация не входят в V1; возраст записи вычисляется для отображения.
- `CONFIRMED TECH-ADMIN-ROLE-001`: канонический пользовательский scope первого выпуска — существующая роль/учётная запись `admin`. Техническая роль `curator`, если присутствует в старой схеме, мигрируется в тот же набор административных разрешений либо становится совместимым alias, но не получает отдельные маршруты, навигацию или связь с учеником. В общих очередях нет assignee/curator ID; автор каждого действия определяется из admin user ID в аудите.

### 8.1 Поставка визуальной системы

До реализации `LEVEL` команда принимает не отдельные картинки по экранам, а один версионируемый комплект:

- единый круглый мастер LEVEL с 10 цветовыми конфигурациями, 1 достижение `MAESTRO` и 5 медалей серии;
- редактируемые дизайн-токены дуги, фона, номера и свечения без отдельных растровых экспортов для каждого экрана;
- таблицу цветов, фонов, контуров и контрастных цветов текста для каждого LEVEL;
- правила размеров для compact, regular и hero-представления;
- состояния `locked`, `next`, `current`, `achieved`, `max`;
- один шаблон анимации повышения LEVEL с десятью цветовыми конфигурациями;
- отдельную кульминацию `LEVEL 10` + `MAESTRO` без создания второй бизнес-награды;
- проверенные desktop/mobile-макеты всех семи компонентов первого выпуска из `SCREEN-LEVEL-001`;
- fallback без анимации для `prefers-reduced-motion` и текстовый fallback при недоступности изображения.

Сезонные компоненты и графика не проектируются и не резервируются в первом выпуске.
- отдельное защищённое исправление 100% в будущем атомарно возвращает тему и план в работу и создаёт отдельные `-100`/`-250` транзакции; интерфейс и право куратора не входят в `DEV-01`;
- та же операция пересчитывает LEVEL и отменяет пользовательскую видимость медалей, полученных только из-за ошибочного баланса;
- исходные награды, исправление, причина и автор остаются в аудите.

## 9. Файлы и безопасность

`CONFIRMED TECH-FILES-001`: production использует приватный S3-совместимый storage adapter, настроенный переменными окружения и не привязанный в доменной модели к конкретному провайдеру. Локальный Docker использует изолированный volume `maestro_local_uploads`; URL локального файла не может ссылаться на production bucket или production API.

Allowlist и значения по умолчанию первого выпуска:

| Тип | MIME | Максимум одного файла |
|---|---|---:|
| Изображение | `image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif` | 15 MB |
| PDF | `application/pdf` | 25 MB |
| Аудио | `audio/mpeg`, `audio/mp4`, `audio/wav`, `audio/webm`, `audio/ogg` | 100 MB |
| Видео | `video/mp4`, `video/webm`, `video/quicktime` | 500 MB |

- одна попытка ДЗ или один отчёт урока содержит не более пяти вложений;
- сервер проверяет заявленный MIME, сигнатуру содержимого, размер и hash; расширение файла не является источником истины;
- до успешной malware-проверки blob имеет статус `quarantined` и не выдаётся пользователям;
- приватная ссылка на скачивание действует 10 минут и создаётся только после повторной server-side проверки scope;
- учебный blob хранится 12 месяцев после закрытия связанного ДЗ/урока, затем удаляется; hash, MIME, размер, автор, связь, время и аудит доступа хранятся три года;
- исходные файлы доступны ученику-владельцу, постоянно назначенному преподавателю в разрешённом направлении и администратору; разовая замена видит только файлы конкретного назначенного урока; родитель исходные файлы не видит;
- публичная публикация учебного файла и постоянная публичная ссылка отсутствуют в V1. Договорное согласие из CRM используется только будущим отдельным процессом публикации и не делает приватное вложение публичным;
- upload, download, quarantine, отказ проверки и удаление содержимого журналируются; системная ошибка создаёт запись общего админского журнала;
- отказ должен возвращать стабильный безопасный код ошибки и понятное действие повторной загрузки без раскрытия внутреннего пути storage.

`CONFIRMED TECH-FILES-002`: UI загрузки показывает прогресс, допустимые форматы/размер до выбора, состояние проверки, безопасную ошибку и повтор. Скачивание проверяется отдельным API-контрактом; прямой путь `/uploads/...` не является правом доступа.

Сложность полноценного контура файлов: `L`. Связи V1: ДЗ, урок, чат и права доступа.

## 10. Миграция и совместимость

Миграция должна отдельно классифицировать:

- опубликованные месячные планы;
- текущие и прошлые пункты планов;
- очные ДЗ, восстановленные из отчётов уроков;
- курсовые попытки;
- онлайн-задания и попытки;
- баллы, XP, Coins и достижения;
- старые ссылки уведомлений;
- активных, ушедших и вернувшихся учеников.

`CONFIRMED TECH-029`: открытые очные ДЗ, созданные до cutover, остаются активными в существующем маршруте и не конвертируются автоматически в новые ДЗ или темы.

- ученик может завершить старое открытое ДЗ после cutover;
- преподаватель может проверить и закрыть его;
- результат и история сохраняются;
- новая формула Points, XP и Coins к такому ДЗ не применяется;
- разделение старого и нового маршрутов определяется временем создания ДЗ и покрывается тестами границы cutover.
- старые результаты остаются в отдельной legacy-проекции; новая статистика читает только назначения новой модели после cutover и не пытается восстановить отсутствующие версии/циклы задним числом.

`CONFIRMED TECH-030`: для каждого ученика/группы и направления мигрируется последняя опубликованная версия незавершённого плана. Миграция создаёт один активный `MonthlyPlan`, нормализованные темы и историю исходных процентов, а исходный документ сохраняет как read-only legacy snapshot. Неопубликованные черновики не становятся активными.

- тема с исходным процентом 100 получает признак импортированного закрытия и использованный/неподходящий reward source, поэтому повторные 100 Points невозможны;
- тема ниже 100 сохраняет процент и может получить 100 Points только при первом явном закрытии после cutover;
- прежний признак или транзакция награды плана переносится; +250 Points разрешены только при отсутствии прежнего начисления и первом завершении новой проекции;
- повторный запуск миграции использует стабильные legacy source IDs и не создаёт второй план, тему, историю или награду;
- dry-run сообщает количество перенесённых планов и тем, число уже закрытых тем, планы с найденной прежней наградой и неоднозначные записи для ручной проверки.

`CONFIRMED TECH-ECONOMY-CUTOVER-001`: новая экономика использует отдельный `epochId`. На cutover все активные ученики из CRM-проекции получают opening state новой эпохи: `Points = 0`, `LEVEL = 1`, `weeklyXP = 0`, `Coins = 200`. Старые ledger rows не удаляются, но запросы текущего баланса, профиля и лидерборда фильтруются по новой эпохе. Для каждого ученика создаётся стабильный source key `economy-v2-opening:2026-09-07:{studentId}`; повторный dry-run/execute не создаёт вторую запись и не меняет 200 Coins. Отчёт показывает число активных учеников, opening entries, пропуски, дубли и контрольные суммы до/после.

## 11. Стратегия внедрения

`CONFIRMED` последовательность поставки:

1. Контракты сущностей, права, события и тестовый каркас - `L`.
2. Темы, планы и рабочий экран ученика - `XL`.
3. ДЗ, попытки, проверки и файлы - `XL`.
4. Единый урок и CRM-синхронизация - `XL`.
5. Points, `LEVEL 1–10`, недельная лига, серия, награды, уведомления и новая экономическая эпоха - `L`.
6. Расширение админки функциями куратора и родительский доступ - `XL`.
7. Учебный диалог - `L`.
8. CRM-групповой чат и модерация - `XL`; общий школьный чат, student-to-student DM, портфолио и будущие модули отложены.

Каждый этап должен быть вертикальным: схема, API, интерфейс, миграция, аудит,
тесты, feature flag и rollback. К каждому пакету прикладывается `removal
manifest`: заменяемые route/component/API/field, временный adapter, условие его
удаления и тест отсутствия второй формулы. Пакет не принимается, если новая
сущность постоянно работает параллельно со старой сущностью того же смысла.
