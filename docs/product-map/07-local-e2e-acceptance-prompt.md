# Локальная сквозная приёмка Maestro

Статус: `QA FOUNDATION READY / DEV-07E COMMUNICATIONS UI AUTOMATED LOCALLY`
Назначение: отдельный исполняемый промпт для проверки приложения от имени всех ролей на локальной базе
Основание: документы [01](./01-product-constitution.md), [02](./02-role-screen-map.md), [03](./03-process-event-map.md), [04](./04-technical-change-map.md), [05](./05-development-prompt.md), [06](./06-next-step-learning-core.md)

## 1. Цель

Поднять Maestro локально, создать воспроизводимую школу с несколькими ролями и прогнать приложение от входа до итоговых транзакций. Проверка должна находить не только падения, но и неверные права, потерянные состояния, дубли, неправильные начисления, непонятные кнопки, мобильные переполнения и расхождения между UI, API, базой, CRM-проекцией и аудитом.

Исполнитель не ограничивается отчётом о дефекте: он локально исправляет обнаруженную проблему, добавляет автоматическую защиту и повторяет затронутый сценарий и общий smoke. Продуктовые правила не додумываются. Если поведение отсутствует в документах 01–06 и влияет на пользователя или деньги, оно выносится отдельным вопросом владельцу продукта.

## 2. Жёсткая граница безопасности

- Использовать только два локальных репозитория: `/Users/vladislav/Documents/Maestro/projects/maestro-learning-platform` и `/Users/vladislav/Documents/Maestro/projects/maestro-crm`.
- Поднимать оба контура через их `docker-compose.local.yml` с отдельными локальными volumes PostgreSQL, Redis и uploads.
- Не выполнять mutating-запросы к production, CRM production, shop production или публичному API.
- Не копировать production-базу по умолчанию. Основной прогон использует синтетический seed без персональных данных.
- Анонимизированный снимок production допустим только после отдельного явного разрешения владельца и отдельной проверки, что в нём нет ФИО, телефонов, файлов, сообщений, токенов, договоров и платёжных данных.
- Не выполнять commit, push, deploy и изменение production-конфигурации.
- Секреты тестовых аккаунтов существуют только в локальном `.env`/fixture-конфиге и не попадают в отчёт или репозиторий.
- Любая команда очистки должна затрагивать только volumes проекта `maestro-local`.

В проекте уже есть:

- полноценный соседний `maestro-crm/docker-compose.local.yml` с PostgreSQL на `5433`, Redis на `6379`, CRM API на `5001` и frontend на `8080`;

- Playwright-smoke `homework-v2-responsive.spec.ts` для карточки ученика, очереди и карточки проверки на desktop и `320/375/430/768 px`;
- защищённый `e2e:lesson-v2-rewards`, который подтверждает однократные `100 Points` за закрытие темы, два attendance-события по `20 XP` и недельный лимит третьего занятия;
- Playwright-сценарий `lesson-sync-v2.spec.ts` для `pending_sync`, конфликтного журнала, серверного черновика без `localStorage` и ширин `320/375/430/768 px`;
- feature flags `DEV-01..DEV-08`, выключенные по умолчанию.

Текущие seeds недостаточны для полной приёмки: они не создают согласованный между двумя базами набор из двух преподавателей, индивидуальных и групповых CRM-уроков, полного набора учеников, смен преподавателя, отмен, новой экономической эпохи и управляемых ошибок CRM. Первый технический шаг — добавить отдельные детерминированные QA seeds с общими fixture IDs и локальный CRM fixture controller, не превращая production seeds в демонстрационную базу.

- legacy-экономика с ненулевыми Points/Coins у нескольких учеников для доказательства чистого старта.

### 4.3 Локальная CRM и fixture controller

Проверка использует настоящий локальный backend `maestro-crm`, его Prisma-модель и реальные integration endpoints. Fixture controller является только защищённым QA API/CLI управления локальными данными и часами; он не заменяет CRM бизнес-логику. Обязательные команды:

1. Создать, перенести и отменить урок с причиной.
2. Повторно доставить то же событие с тем же `externalId/version`.
3. Доставить более старую и более новую версию события.
4. Подтвердить и отклонить посещаемость преподавателя.
5. Назначить разовую замену конкретного урока.
6. Завершить постоянное назначение и назначить нового преподавателя.
7. Изменить состав группы до и после сохранения черновика.
8. Включить outage, timeout и восстановление CRM.
9. Задержать событие до понедельника и доставить до/после финализации недели.
10. Передать каникулы, паузу абонемента и отмену всех уроков недели.
11. Передать договор родителя, новую версию, окончание и отзыв согласия.

Controller обязан проверять `MAESTRO_QA_LOCAL=true`, marker локальной CRM-базы и разрешённые fixture-префиксы до любой записи. Он только управляет CRM-owned данными и подтверждениями; production endpoint и production database URL должны приводить к немедленному отказу.

## 5. Порядок выполнения

### QA-00. Чистый старт и baseline

1. Зафиксировать текущий `git status` обоих репозиториев без изменения пользовательских файлов.
2. Собрать образы, поднять сначала локальную CRM, затем Learning Platform и дождаться health всех сервисов.
3. Применить migrations/production-safe seeds обоих приложений, затем согласованные QA seeds с одинаковыми CRM/app fixture IDs.
4. Запустить backend tests, typecheck обоих приложений и существующие E2E scripts.
5. Проверить `/health`, `/login`, авторизацию admin и отсутствие соединений с production hosts.
6. Сохранить версии образов, feature flags, seed version и время `Asia/Aqtobe` в локальный отчёт прогона.

### QA-01. Авторизация и права

Проверить вход/выход и прямые URL каждой роли. Ученик не открывает admin API; преподаватель не видит чужого ученика, финансы и зарплату; родитель не видит попытки, файлы, личный диалог и Coins-действия; разовая замена не видит общую историю; admin видит школу из существующей админки. Каждый запрет проверяется через UI и прямой API-запрос, чтобы скрытая кнопка не подменяла RBAC.

### QA-02. Админка и общий журнал

1. Убедиться, что отдельного кабинета/назначения куратора нет.
2. Проверить пять первых разделов: обзор, учебный контроль, коммуникации, люди, журнал.
3. Создать записи журнала из жалобы, CRM-ошибки, зависшей проверки, зависшего отчёта, корректировки награды и изменения родительского доступа.
4. Проверить сортировку severity/возраст, фильтры и статусы `new`, `in_progress`, `resolved`, `dismissed`.
5. Проверить отсутствие assignee и наличие фактического admin-автора в неизменяемой истории.
6. Начислить 1 и 1 000 Coins за разные подтверждённые события; 0, 1 001, пустая причина и повтор source key должны отклоняться.

### QA-03. Индивидуальный урок преподавателя

Прогнать урок полностью: открыть, восстановить черновик после перезагрузки, отметить посещение, открыть прошлое ДЗ, принять/вернуть его, изменить тему на 0–99%, отдельно подтвердить 100%, заполнить итог, создать ДЗ с предлагаемым сроком и без срока, просмотреть отчёт и отправить.

Негативные варианты:

- не заполнить обязательный итог/посещаемость и убедиться, что отправка блокируется у конкретного поля;
- не создавать новое ДЗ и успешно завершить урок, если домашняя работа не выдавалась;
- вернуть ДЗ без комментария и получить валидацию;
- принять ДЗ, но оставить тему на 70%;
- закрыть тему на 100% без ДЗ, если тема реально пройдена на уроке;
- попытаться начислить Points второй раз повтором запроса;
- отозвать неподтверждённый отчёт, исправить и отправить новую версию;
- после подтверждения CRM проверить отсутствие самостоятельного редактирования преподавателем и административное переоткрытие с причиной.

### QA-04. Групповой урок

Проверить компактную форму: одна тема и процент группы, одно прошлое общее ДЗ, строки участников с галочкой посещения, индивидуальным статусом сдачи, решением проверки и раскрываемым комментарием. Новое ДЗ назначается всем активным участникам, включая отсутствовавшего. У каждой попытки и проверки свой ученик, но тема не копируется и не получает три разных процента.

Отдельно проверить изменение roster после сохранения draft, архивированного ученика, ученика без ответа, доработку одного участника и отсутствие горизонтальной прокрутки на 320/375/430 px.

### QA-05. Отмена, перенос и замены

1. Отменить будущий урок через fixture controller реальной локальной CRM и проверить расписание, уведомление, отсутствие списания/XP/Coins и правильную причину.
2. Повторно доставить отмену и доказать отсутствие дубля.
3. Создать новый урок вместо отменённого: это новый CRM ID и отдельное событие, а не возврат финансов старого.
4. Перенести следующий урок и доказать, что уже сохранённый срок ДЗ не меняется молча.
5. Дать `QA-TEACHER-2` разовую замену: доступ только к уроку/отчёту, без истории, очереди ДЗ и чатов.
6. Выполнить постоянное переназначение: открытые ДЗ и разрешённая история переходят новому преподавателю, старый теряет доступ, авторство сохраняется.

### QA-06. Маршрут ученика

1. Проверить одно главное действие и дедупликацию карточек на главной.
2. Отправить текст, файл, аудио и видео; обновить ответ до проверки как новую неизменяемую версию одной строки очереди.
3. Нажать «Я подготовил» без текста/файла и увидеть «Проверить на уроке» без награды.
4. Получить доработку, увидеть официальный комментарий, отправить новую попытку и затем получить принятие.
5. Проверить историю темы, ДЗ, версии, проценты и награды без смешивания legacy-блока.
6. Проверить магазин в тенге и вкладку Coins, недостаточный баланс, ручное подтверждение/отказ и полный возврат Coins при отказе без складского резерва.
7. Проверить скачивание разрешённого материала урока и понятную ошибку для удалённого/quarantined файла.

### QA-07. Родитель

Оба родителя видят одинаковый компактный read-only обзор: ближайшее расписание,
одну CRM-сумму со знаком, процент плана, полученные достижения и родительские
новости. Они не видят ДЗ, попытки, файлы и личный учебный диалог ребёнка,
внутренние заметки, LEVEL, Points, XP, Coins, магазин и других учеников. Оба
родителя видят одну общую переписку с постоянным преподавателем по ребёнку и
направлению; ребёнок её не видит. Отзыв одного
родительского аккаунта не отзывает второй; политика видимых разделов при этом
остаётся единой для ребёнка.

### QA-08. Экономика, LEVEL и рейтинги

Перед cutover fixture содержит разные старые балансы. После однократного открытия новой эпохи каждый активный ученик имеет ровно:

- `0 Points`;
- `LEVEL 1`;
- `0 XP` текущей недели;
- `200 Coins`.

Повтор cutover не меняет значения. Legacy-ранг, Points и Coins не видны в текущем профиле, текущем top по Points и магазине, но доступны административному аудиту.

Затем проверить транзакции по одной и в комбинации:

| Источник | Ожидание |
|---|---|
| первое и второе подтверждённые занятия недели | по 20 XP и 50 Coins |
| третье занятие | 0 XP/Coins, но подходит для серии |
| принятое ДЗ с первой попытки | 15 XP |
| принятое ДЗ после возврата | 10 XP |
| четвёртое принятое ДЗ одного направления за неделю | 0 XP |
| первый/повторный успешный тест | 20/10 XP, максимум два теста |
| бонус преподавателя | 1–10 XP, суммарно не больше 10 за неделю |
| первая тема на 100% | 100 Points один раз |
| завершение непустого плана | 250 Points один раз |
| цель 80 XP | 25 Coins один раз |
| места 1/2/3 после финализации | 150/100/50 Coins |
| рубежи серии 4/8/12/24/52 | 50/100/150/250/500 Coins и медаль один раз |

Проверить LEVEL-пороги, `MAESTRO` на LEVEL 10, продолжение Points после максимума и обратные административные транзакции. Недельная таблица XP и отдельный «Топ по Points» должны иметь разные источники, подписи и последствия; равные Points дают равную позицию.

### QA-09. Неделя, задержки и серия

Смоделировать границу воскресенье/понедельник в `Asia/Aqtobe`, `finalizing` до 12:00, событие CRM до и после финализации, идемпотентный повтор finalization job и неизменяемый snapshot. После 12:00 позднее событие не меняет места/Coins автоматически. Административная компенсация и reversal записываются отдельно.

Проверить обычный сброс серии, автоматический freeze на каникулах/паузе/отмене всех занятий, ручное исключение в течение семи дней и отказ позже срока. Frozen week не увеличивает и не сбрасывает серию, не даёт награду и не приближает медаль.

### QA-10. CRM offline, конфликт и повтор

При outage ранее известный урок проводится и сохраняет `pending_sync`; списание, зарплата и XP отсутствуют до подтверждения. После восстановления очередь доставляется один раз. Неизвестный локальной проекции урок создать нельзя. Проверить старую версию события, расхождение посещаемости, конфликт без владельца, сохранение обеих версий, административное решение с причиной и запись журнала.

### QA-11. Вложения и скачивание

Проверить каждый разрешённый MIME возле лимита, запрещённое расширение/сигнатуру, превышение размера, шестой файл, malware/quarantine, истёкшую ссылку, повторную server-side авторизацию и удаление blob по retention job. Назначенный преподаватель скачивает файл; чужой преподаватель, родитель и ученик другого аккаунта получают `403/404` без утечки пути. Разовая замена скачивает только файл конкретного урока. Все взрослые скачивания видны в аудите.

### QA-12. Коммуникации и модерация

Проверить учебный диалог постоянного назначения, единый parent-teacher диалог двух родителей, обращение к общей админке и CRM-группу. Разовая замена не получает чат. Старые учебный и родительский диалоги после постоянной смены read-only и недоступны новому преподавателю; возврат того же преподавателя продолжает прежние scope. Проверить edit/retract 15 минут, жалобу на конкретную версию, скрытие с причиной, временное ограничение группы без ручного изменения CRM-состава, до пяти изображений/видео MP4-MOV-WebM/PDF/аудио по 50 MB и отсутствие student-to-student DM/общего школьного чата.

### QA-13. Интерфейс глазами пользователя

Через in-app browser/Playwright пройти все основные экраны desktop и 320, 375, 430, 768 px. Проверить отсутствие горизонтальной прокрутки, обрезанных кнопок, длинных колонок, перекрытия текста, скачков layout и кнопок без результата. На каждом экране проверить loading, empty, partial error, permission denied, offline и long-content состояния. Для главной ученика, группового урока, очереди проверки, админского журнала, лиги/top Points и карточки файла сохранить screenshots.

Отдельно проверить сокращение интерфейса:

## 7. Цикл исправления

Для каждого дефекта:

1. Зафиксировать роль, исходные данные, шаг, ожидаемое и фактическое поведение.
2. Добавить минимальный воспроизводящий автоматический тест.
3. Исправить корневую причину в существующей архитектуре.
4. Прогнать воспроизводящий тест, затронутый пакет и общий smoke.
5. Проверить UI на desktop/mobile, если дефект видим пользователю.
6. Записать результат и остаточный риск; не закрывать дефект только по визуальному впечатлению.

Критический дефект останавливает дальнейшее начисление/изменение данных до исправления. Некритические UI-дефекты можно группировать, но они всё равно должны пройти повторную визуальную проверку.

## 9. Критерий готовности

Локальная версия готова к отдельному обсуждению релиза только когда:

1. Все применимые сценарии QA-00…QA-14 проходят на чистой базе и после повторного запуска.
2. Нет неизвестных начислений, дублей, отрицательного баланса без reversal или расхождения UI/API/ledger.
3. Все роли проходят и положительные, и отрицательные проверки доступа.
4. CRM outage/retry/cancel/reschedule и обе замены не теряют данные.
5. Вложения загружаются и скачиваются только разрешёнными участниками.
6. Админка является единственным кабинетом куратора, а общий журнал собирает предусмотренные исключения.
7. Desktop/mobile screenshots не содержат переполнения и перекрытия.
8. В отчёте нет `blocked` без решения владельца продукта.

Даже после выполнения этих условий документ не разрешает commit, push или production deploy. Для них требуется отдельная явная команда владельца.
