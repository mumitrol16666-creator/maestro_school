# Регламент выполнения плана: что делает модель на каждом пункте

Дата: 19.10.2026. Относится к плану `13-work-plan-2026-10-17.md`, пункты 1.4–1.13 и дальше.
Это инструкция для модели (Claude в Claude Code), а не для людей: какие этапы пройти,
что проверить и как отчитаться, чтобы пункт считался сделанным.

## 1. Границы, которые не нарушаются ни на одном пункте

| Норма | Что это значит в коде | Как проверяется |
|---|---|---|
| Деньги только в CRM | Приложение не считает списания, зарплату, тарифы и остатки. Подтверждение урока и возврат только через CRM, платформа лишь принимает колбэк и опрашивает | В платформе нет новых полей с суммами; родитель видит одну сумму `amountDueKzt` из CRM |
| Учитель Points не трогает | Исключение по решению 19.10: число баллов при досрочном закрытии сектора. Остальные Points только автоматом: тема 100 % → 100, сектор → 250 | Нет полей ввода Points в уроке и карточке, кроме плашки досрочного закрытия |
| Награды идемпотентны и откатываемы | Каждое начисление с уникальным `sourceKey`; откат переименовывает ключ в `…:reversed:v<n>` свободным суффиксом и пишет обратную проводку | DB-тест на повторный вызов и на откат; сценарий возврата урока 0.2 |
| Замена преподавателя (LEARN-026, решение 19.10) | Флаг «замена» с назначения на урок до подтверждения; после — доступ закрыт. Постоянный учитель не ограничен | Тест: чужой учитель 403, заменяющий видит, после подтверждения снова 403 |
| Родитель видит только своё | Баланс одной суммой, расписание, прогресс сектора с процентами тем, достижения. Никаких ДЗ-очередей, комментариев учителя и внутренних статусов | `ParentVisibilityPolicy`, тест `family-view.test.ts` |
| Ученик до подтверждения админом ничего не видит по уроку | Тема, итог, ДЗ и материалы появляются после `confirmed` | Проверка роли ученика на QA-контуре после submit без approve |
| Legacy не показывается в V2 | Все 9 флагов V2 на проде включены; legacy-ветки остаются только для истории до cutover | В новых экранах нет `monthlyPlan`, `lessonPoints 0–100`, `StudentLearningResultFields` |
| Прод и push только после вопроса | Коммиты в ветки `codex/stage0-approve-callback-20261017` обоих репозиториев, без push и без PR, пока Владислав не скажет | В отчёте всегда «закоммичено, не запушено» |
| Язык и тон интерфейса | Русский, обращение на «вы» к учителю и родителю, на «ты» к ученику; тексты короткие; никаких «план месяца» | Grep по старым формулировкам перед коммитом |

## 2. Этапы на каждый пункт плана

1. **Прочитать.** Пункт в документе 13, решения Владислава под ним, документ 02 для экрана, карту 12 для текущего кода. Если решение противоречит другому — задать вопрос до кода, не угадывать.
2. **Спроектировать и записать.** Короткий дизайн: данные, маршруты, экраны, кто что видит. Допущения выписать явно; то, что меняет суть, спросить. Пункт разбить на шаги в задачнике сессии.
3. **База.** Изменение `schema.prisma` + миграция с `IF NOT EXISTS`, где можно. Проверить `prisma migrate diff` после `migrate deploy` на тестовой базе: по новым таблицам дрейфа нет. Старые данные не удалять: архивная схема или новые колонки с `null`.
4. **Бэкенд.** Сервис → маршрут → zod-схема. Доступ проверяется в сервисе (CRM-ростер, урок, роль), а не в маршруте. Ключи наград уникальные, откат предусмотрен сразу. Старый формат входных данных принимается, если он мог остаться в черновиках или отчётах.
5. **Тесты бэкенда.** Юнит-тест на правило домена, DB-тест на сценарий (создать фикстуру, вызвать сервис, проверить строки, удалить фикстуру). Полный прогон `npm test` с `RUN_DB_INTEGRATION_TESTS=1` на `maestro_platform_stage0_test`: 0 падений, пропуски объяснимы.
6. **Web.** Типы → API-клиент → компонент → страница. Тексты по норме языка. Экран работает на 320–430 px без горизонтальной прокрутки, кнопки не ниже 44 px, у кнопок-иконок `aria-label`. `npm run lint` (это `tsc --noEmit`) без ошибок.
7. **QA-контур.** Postgres 5432, CRM 5002, платформа 4001, web 3320 (рецепт в памяти `maestro-qa-stack-nodocker`). После правок бэкенда API перезапускается, миграция накатывается на `maestro_regression`, при необходимости `qa-seed` и `economy:v2:cutover:apply`. Перед сценариями наград чистить проводки `%QA-RUN-%`, между скриптами пауза 40–75 с из-за лимита логина.
8. **Проверить руками и спекой.** В браузере пройти экран за ту роль, для которой он сделан. Playwright-спека на главный путь (через системный Chrome, конфиг `playwright.chrome.config.ts`). Сквозные скрипты, которых касается пункт: approve 0.1, возврат 0.2, групповая тема 0.3, сектор, карточка, урок по шагам.
9. **Записать.** Статус в документе 13 под пунктом, запись в памяти, коммит с описанием «что и почему», без push. Если что-то не проверено, так и написать в коммите и в отчёте.
10. **Отчитаться.** Первая строка «Да/Нет». Что изменилось для учителя, ученика, родителя. Что проверено и чем. Что не сделано или не проверено. Вопросы, если появились.

## 3. Что проверить по каждому пункту плана

### 1.4 «Сегодня» для учителя
- Экран `/admin` у роли учитель: уроки дня по времени с «Начать», незакрытые отчёты (editing, returned), работы на проверке, новые предложения в сектор, сообщения без ответа, дни рождения на неделе.
- Просрочки: отчёт не отправлен через сутки после урока, работа ждёт проверки дольше урока, предложение без ответа 3 дня. Каждая просрочка — уведомление учителю (`UserNotification`), не чаще раза в день на объект.
- Проверить: пустой день, день с 5 уроками, CRM недоступна (экран живёт на кеше и говорит об этом), учитель-замена видит только свой урок.

### 1.8 Мелкие решения
- Досрочное закрытие: кнопка в редакторе сектора, плашка с числом 0–250, запись в `closeReason = manual`, проводка Points с ключом `learning-plan-completion:{plan}:{student}` на введённую сумму, откат как у обычного закрытия. Следующий сектор открывается только после закрытия. Тест: 0 баллов, 250 баллов, повтор не удваивает.
- Лимит бонуса: `POST /teacher/weekly-league/bonus` отказывает вторым бонусом тому же ученику на той же неделе Актобе кодом `BONUS_WEEKLY_LIMIT`; карточка и «Мои ученики» показывают «бонус на этой неделе уже дан».
- Проценты родителю: `family.service` отдаёт `items` с `progressPercent`, экран родителя рисует их. Политика видимости не трогается.
- Повтор контекста: `StudentLessonCheckCard` и `GroupStudentRow` не рисуют `StudentPreviousContext` при степпере.
- Архив таблиц: миграция переносит `student_monthly_plans`, `group_monthly_plans` в схему `legacy_archive`, код и Prisma-модели удаляются, `scripts/product-baseline.ts` и `learning-topics-v2-migration.ts` правятся или удаляются. Данные остаются, проверка `select count(*)` до и после.

### 1.9 Замена по флагу
- Источник правды — CRM: урок с `teacherId ≠ originalTeacherId` даёт заменяющему флаг на пару (учитель, ученик) с момента назначения до `confirmed`. Хранить в платформе `teacher_substitutions` с `crmClassId`, `validUntil`.
- `requireTeacherHomeworkStudent`, `teacherStudentIds`, карточка ученика, диалоги и ДЗ учитывают флаг. После подтверждения — отказ 403 с понятным текстом.
- Тесты: до назначения 403, во время — полный доступ, после подтверждения 403, у постоянного учителя ничего не меняется. Сценарий на QA-контуре с `QA-TEACHER-2`.

### 1.10 Экзамен сектора, платформа
- Модели: `SectorExam` (сектор, статус, дата урока CRM, автор), `SectorExamItem` (критерий темы или свой пункт, порядок), `SectorExamResult` (ученик, пункт, сделано/нет, кто отметил). Один открытый экзамен на сектор.
- Создание админом приложения в `/admin`: чеклист предзаполнен критериями тем сектора, можно добавить пункты, кнопка «Отправить на назначение» ставит статус `awaiting_schedule` и уходит в CRM (1.11).
- У учителя: «Начать экзамен» только когда все темы сектора 100 % и экзамен назначен; отметки по ученику; «Завершить сектор» и «Пересдача» при любом исходе; `preparedTestId` и `testPassedAt` из сектора уходят, готовые тесты остаются отдельным экраном.
- Баллы: 250 за закрытие сектора без изменений; экзамен даёт сертификат (запись + PDF позже), не Points.
- Ученик и родитель видят дату экзамена и результат по пунктам.
- Тесты: нельзя начать без 100 %, повторный результат идемпотентен, пересдача создаёт новый экзамен со ссылкой на прошлый.

### 1.11 Экзамен сектора, CRM
- В CRM: таблица ожидающих экзаменов из платформы (интеграционный маршрут с `INTEGRATION_SERVICE_SECRET`), плашка в разделе подтверждения уроков, «Назначить экзамен» в свободном слоте расписания со списком ожидающих, тип урока `exam`, цена 0, без списания.
- После назначения: колбэк в платформу (дата, `crmClassId`), уведомления админу, учителю, ученикам; черновики WhatsApp ученикам и родителям через существующий механизм `whatsapp/homework-drafts`.
- Тесты CRM (`npm test` с `TEST_DATABASE_URL`) и сквозной скрипт: создать экзамен → назначить → колбэк → провести → завершить сектор.

### 1.12 Библиотека материалов
- Модель `MaterialLibraryItem` (url, подпись, тип видео/фото/файл/ссылка, кто добавил), общая на школу; загрузка в `/admin/media` и из урока.
- В уроке и ДЗ: поле материала с подсказками по подписи, тип показан пометкой (MP4, PNG, ссылка). YouTube и Vimeo у ученика встраиваются, остальное открывается ссылкой.
- «Отправить урок курса»: материал со ссылкой на урок курса; ученик открывает голый урок для просмотра, без «сдать» и прогресса курса.
- Папка загрузок: статическая раздача закрывается, файлы отдаются через API с авторизацией; проверить, что старые ссылки в материалах переписаны.

### 1.5–1.7 Из старого плана
- Бонус XP на шаге «Итог»: та же форма, что в карточке; лимит из 1.8.
- Быстрая тема: добавляется только в опубликованную версию сектора, направление обязательно.
- Мёртвое: `coins.award`, `teacherOfflineApi.finish`, legacy онлайн-заявки, «Взять заявку», 14 legacy-достижений, флаг `studentWorkspaceV2` — удалить, прогнать все тесты.

### 1.13 Сектора групп
- Не делать до 1.10. Спроектировать по предложению «Личный сектор и сектор группы» в документе на телефоне, получить ответы на три вопроса, затем план.

## 4. Как выглядит «сделано» для пункта

- Код в ветке, коммит с описанием, без push.
- Типы обоих приложений зелёные, тесты бэкенда без падений, Playwright-спека пункта зелёная на QA-контуре, ручная проверка за нужную роль.
- Документ 13: строка «Статус … сделано» под пунктом; память обновлена.
- Отчёт Владиславу: что изменилось, чем проверено, что осталось, вопросы.
