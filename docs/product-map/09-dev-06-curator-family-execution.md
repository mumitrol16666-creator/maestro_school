# DEV-06: общая админка и родительский доступ

Статус: `DEV-06A..DEV-06D DONE LOCALLY / DEV-07A..DEV-07D DONE / READY FOR DEV-07E`
Назначение: исполняемая карта функций куратора внутри существующей admin-роли и безопасного read-only доступа родителей
Основание: [01](./01-product-constitution.md), [02](./02-role-screen-map.md), [03](./03-process-event-map.md), [04](./04-technical-change-map.md), [05](./05-development-prompt.md), [07](./07-local-e2e-acceptance-prompt.md)

## 1. Жёсткая граница

- отдельная роль, учётная запись, навигация или кабинет куратора не создаются;
- персонального `curatorId`, assignee и распределения учеников по кураторам нет;
- автор действия всегда является фактическим пользователем существующей admin-роли;
- функции включаются локально через `FEATURE_CURATOR_WORKSPACE_V2`;
- чаты и модерация сообщений относятся к `DEV-07`, а не реализуются внутри DEV-06;
- production, commit, push и deploy не затрагиваются.

## 3. DEV-06A: модель журнала

`AdminJournalEntry` хранит:

- стабильный идемпотентный `sourceKey`;
- тип, важность и источник;
- тип и ID связанного объекта;
- заголовок и краткое описание без технического stack trace;
- статус `new / in_progress / resolved / dismissed`;
- решение, даты создания и обновления.

`AdminJournalAction` хранит неизменяемую историю:

- создание, изменение статуса и системное разрешение;
- исходный и новый статус;
- комментарий/решение;
- фактического admin-автора и время;
- безопасный технический payload без секретов и персональных файлов.

Поле ответственного отсутствует. Список сортируется по важности, затем по возрасту и поддерживает фильтры по типу, важности, источнику и статусу.

## 4. Источники DEV-06A

Первый сквозной пакет подключает:

- неуспешную доставку и конфликт CRM outbox;
- автоматическое закрытие CRM-записи после успешной доставки/разрешения;
- создание, повторное включение и отзыв родительского доступа.

Жалобы/модерация подключаются в `DEV-07`. Зависшие проверки и отчёты будут подключены отдельным адаптером после утверждения порога возраста; DEV-06A не придумывает SLA.

## 5. API и права

- `GET /admin/journal` — список, фильтры и агрегаты;
- `GET /admin/journal/:entryId` — запись и полная история;
- `PATCH /admin/journal/:entryId/status` — изменение статуса с обязательным решением для `resolved/dismissed`;
- student, parent и teacher получают отказ через прямой API-запрос;
- техническая legacy-роль `curator` может использовать тот же API только как alias существующего административного scope.

## 6. Интерфейс

Маршрут `/admin/journal` содержит:

- компактные счётчики открытых записей;
- фильтры типа, важности, источника и статуса;
- плотный список без вложенных карточек;
- возраст записи, связанный объект и текущий статус;
- раскрываемую неизменяемую историю;
- одно явное действие изменения статуса с причиной.

На ширинах 320/375/430 px интерфейс строится одной колонкой без горизонтальной прокрутки.

## 7. Приёмка DEV-06A

1. Повтор одного `sourceKey` не создаёт вторую запись или второе действие создания.
2. Critical/high идут выше normal/low; внутри важности старые записи идут первыми.
3. В модели, API и UI отсутствует assignee.
4. `resolved/dismissed` без решения отклоняются.
5. Каждое изменение хранит фактического автора и не изменяет прошлые действия.
6. CRM retry и родительский доступ создают/закрывают запись идемпотентно.
7. Teacher, parent и student не читают и не меняют журнал через прямой URL/API.
8. Backend/web build, профильный E2E и desktop/mobile Playwright проходят локально.
9. После прогона fixture удалён, flag выключен, production не затронут.

## 9. DEV-06B/06C: подтверждённый контракт

- одна `ParentVisibilityPolicy` принадлежит ребёнку, а не отдельному родителю;
- независимо переключаются расписание, баланс, план и достижения;
- отсутствие строки политики означает безопасный утверждённый default: четыре блока видимы;
- ученик может создать только один ожидающий `ParentVisibilityRequest` и не применяет его;
- admin одобряет/отклоняет запрос с причиной либо меняет политику напрямую;
- оба действия попадают в общий журнал типа `parent_access`;
- родителю отдаётся server-side отфильтрованный read-model без ДЗ, попыток, файлов, чатов, LEVEL, Points, Coins и служебных полей;
- финансовый блок содержит одно `signedAmountKzt`: долг отрицательный, внесённый остаток положительный, ноль означает отсутствие задолженности;
- расписание и деньги принадлежат CRM, план и достижения принадлежат приложению;
- публикация новости имеет независимые флаги «Ученикам» и «Родителям»; разрешена отдельная родительская публикация.

## 10. API DEV-06B/06C

- `GET /students/me/parent-visibility`;
- `POST /students/me/parent-visibility-requests`;
- `GET/PATCH /admin/students/:id/parent-visibility`;
- `POST /admin/students/:id/parent-visibility-requests/:requestId/decision`;
- `GET /parents/me/children/:studentId/offline-summary`;
- `GET /parents/me/news`.

Student не имеет прямого PATCH, parent не создаёт student-запрос и не читает admin API. Несколько родителей одного ребёнка получают одну политику и одинаковую аудиторию школьных новостей.
